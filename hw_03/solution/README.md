## 1. Модель данных

### RestaurantsHandbooksService (read-модель)
- **restaurants**: id, name, description, address, rating, is_active, updated_at
- **menu_items**: id, restaurant_id, name, description, price, category, photo_url, is_available, version
- **categories**: id, name, sort_order

Данные денормализованы под выдачу клиенту: в одной записи меню уже лежат цена, категория и URL фото, без JOIN-ов на каждый запрос. Сами файлы фото в БД не хранятся — только `photo_url` на object storage / CDN.

### PartnersService (Command + runtime)
- **partner_applications**: id, legal_name, brand_name, inn, contact, status, created_at
- **menu_versions**: id, restaurant_id, items (jsonb), status (draft/moderation/approved), moderated_by
- **restaurant_orders**: order_id, restaurant_id, status (pending/accepted/rejected), accepted_at, reject_reason

### OrdersService
- **orders**: id, user_id, restaurant_id, status, pricing_snapshot (jsonb), delivery_address (jsonb), created_at, updated_at
- **order_items**: id, order_id, menu_item_id, name, quantity, price_at_order
- **order_status_history**: id, order_id, status, changed_at, reason

`order_id` составной: префикс шарда + уникальная часть (см. §3). В `pricing_snapshot` сохраняется полный расчёт на момент создания заказа — это страховка, если Pricing недоступен повторно.

### PricingService
- **pricing_rules**: id, type (delivery/service_fee), conditions (jsonb), value, active_from, active_to
- **promo_codes**: code, discount_type, value, max_uses, used_count, valid_until, restaurant_id (nullable)

`used_count` / `max_uses` — инвариант «промокод нельзя применить больше N раз». Источник истины — PostgreSQL (транзакция `UPDATE ... WHERE used_count < max_uses`). Redis хранит только кэш правил, не счётчик.

### PaymentsService
- **payments**: id, order_id, user_id, amount, currency, status (authorized/captured/refunded/failed), provider_payment_id, created_at
- **payment_events**: id, payment_id, event_type, payload, created_at
- **courier_payouts**: id, courier_id, amount, period, status

### CouriersService
- **couriers**: id, user_id, status (online/offline/busy), current_order_id, rating, vehicle_type, home_zone
- **courier_assignments**: id, order_id, courier_id, assigned_at, completed_at

### CourierGeoService
- **courier_locations** (горячие): courier_id, zone_id, geohash, lat, lng, accuracy, updated_at
- **location_history**: courier_id, lat, lng, recorded_at (короткий TTL, аналитика)

### ChatsService
- **conversations**: id, order_id, participants, created_at
- **messages**: id, conversation_id, sender_id, sender_role, text, created_at, is_read

### NotificationsService
- **notification_templates**: id, type, channel, body_template
- **notification_log**: id, user_id, order_id, channel, status, sent_at

## 2. Выбор БД

| Сервис | Что хранит | Форма данных | Ключевые запросы | Выбранная БД | Почему именно она |
|--------|------------|--------------|------------------|--------------|-------------------|
| OrdersService | заказы, позиции, история статусов | реляционная, транзакции | по order_id, по user_id, смена статуса | **PostgreSQL** | ACID при создании заказа и смене статусов, JOIN, целостность |
| PaymentsService | платежи, hold/capture, выплаты | реляционная, деньги | по order_id, аудит | **PostgreSQL** | Строгая консистентность денежных операций |
| PartnersService | заявки, меню на запись, accept/reject | реляционная | по restaurant_id | **PostgreSQL** | Транзакции модерации и принятия заказа |
| CouriersService | курьеры, назначения | реляционная | по courier_id, свободные | **PostgreSQL** | CRUD + связи, небольшой объём |
| RestaurantsHandbooksService | каталог | реляционная + денормализация | по restaurant_id, лента | **PostgreSQL + Redis** | PG — источник текста каталога; Redis — горячий кэш read-модели |
| PricingService | правила, промокоды со счётчиком | реляционная + кэш | расчёт цены, атомарное списание промо | **PostgreSQL + Redis** | PG — истина и транзакция `used_count < max_uses`. Redis — кэш правил расчёта (без счётчика использований) |
| CourierGeoService | текущие координаты | geo / time-series | «ближайшие в зоне», апдейт точки | **Redis GEO по зонам** | Низкая latency и GEORADIUS внутри одной зоны. История — отдельно, короткий TTL |
| ChatsService | сообщения | документы | по order_id, последние N | **MongoDB** | Высокая запись, документ сообщения, JOIN не нужны |
| NotificationsService | шаблоны, лог | простые записи | по user_id / order_id | **PostgreSQL** | Небольшой объём, аудит доставок |
| Фото меню | файлы по `photo_url` | блобы | отдача клиенту | **Object Storage + CDN** | Не кладём картинки в PG/Redis |

Чем жертвуем там, где не PostgreSQL:
- Redis GEO — нет сложных JOIN и долгой истории; координаты можно потерять на секунды.
- MongoDB — нет кросс-документных транзакций между чатами; для сообщений это приемлемо.
- CDN — eventual по инвалидации картинки (старое фото минуту-другую).

## 3. Шардирование

### Шаг 0. Нужно ли шардировать сейчас

Прикидка нагрузки (те же допущения, что потом пойдут в сайзинг):  
DAU 500 000, 2 заказа на пользователя в неделю → **~143 000 заказов/сутки**.

**OrdersService**

```
143 000 заказов/сутки × 8 КБ ≈ 1,1 ГБ сырых строк / сутки
за год ≈ 400 ГБ полезных данных, с индексами и TOAST ≈ 0,8 ТБ
write RPS в пике ≈ 5 (создание) + смена статусов ≈ 15–20
```

0,8 ТБ и 20 write RPS спокойно живут на одном primary PostgreSQL с read-репликами. Шардировать «с первого дня на 4–8 узлов» — лишняя сложность (кросс-шардные запросы, ребалансировка, операционка).

**Старт:** один кластер + **партиционирование `orders` по `created_at`** (месяц/квартал) + 1–2 read-реплики для истории.  
**Шардирование — план на вырост**, когда горячий горизонт перестанет влезать в одну ноду (ориентир: несколько ТБ горячих данных или устойчиво сотни write RPS). Ниже — схема, к которой переходим в этот момент, а не конфиг дня запуска.

**CourierGeoService**

```
15 000 курьеров онлайн в пике × апдейт раз в 5 сек ≈ 3 000 write/сек
полезный объём «текущих точек» крошечный (~МБ), но QPS высокий
запрос «ближайшие» должен отвечать за единицы миллисекунд
```

Здесь шардирование нужно не из-за терабайт, а из-за QPS и локальности geo-запроса. Один Redis GEO на всю страну начнёт упираться в CPU одной ноды и в размазанный индекс.

### 3.1. OrdersService (когда дорастём)

| Параметр | Решение |
|----------|---------|
| Что шардируем | orders + order_items + order_status_history |
| Ключ | `user_id` |
| Стратегия | hash(user_id) → номер шарда |
| Как адресовать заказ | **номер шарда зашит в `order_id`** (префикс / ULID с shard-id) |
| Старт шардов | 4, когда решим включать |
| Ребалансировка | consistent hashing + virtual nodes |

**Почему `user_id`:** запросы «мои заказы» и история пользователя попадают в один шард.

**Как находим заказ по `GET /orders/{orderId}` без lookup-сервиса.**  
Lookup «order_id → шард» — лишняя точка отказа (это прямо сказано в шаблоне). Глобальный вторичный индекс по всем шардам — тот же cross-shard.  
Поэтому `order_id` сразу содержит номер шарда: `s03-01J…`. Роутинг читает префикс. Новый заказ пользователя всегда пишется в шард `hash(user_id)`.

**Hotspot.** Соль к `user_id` не используем: она размажет историю одного человека по шардам и убьёт локальность, ради которой ключ выбран. Переход на `hash(order_id)` — это уже другая схема, не «лечение».  
Конечный клиент в доставке еды не создаёт тысячи заказов в секунду — hotspot по `user_id` маловероятен. Реальный перекос — **популярный ресторан** (много входящих заказов на один `restaurant_id`). Это не ключ шарда, поэтому пик ресторана бьёт по саге и Partners/Kitchen, а не по одному шарду Orders. Если когда-нибудь понадобится резать и это — отдельный контур приёма заказа рестораном, не смена ключа Orders.

**Cross-shard:** связанные строки одного заказа лежат вместе → локальные транзакции. Запрос «все заказы ресторана за час» — scatter-gather или отдельная read-модель, сознательно не оптимизируем шардом Orders.

### 3.2. CourierGeoService

| Параметр | Решение |
|----------|---------|
| Что шардируем | текущие координаты |
| Ключ | **зона доставки / город + geohash-префикс** |
| Стратегия | geo-шардирование, не hash(courier_id) |
| Почему не hash(courier_id) | апдейты локальны, но главный запрос — `GEORADIUS` / «ближайшие к точке». Соседние курьеры при hash разъезжаются по разным шардам → каждый поиск становится scatter-gather. |

Курьер пишет точку в шард своей текущей зоны. Поиск ближайших идёт **только в шард этой зоны** (и при необходимости в соседей по geohash, 1–2 шарда на границе, не все).

**Hotspot, который здесь реален:** Москва vs маленький город. В одном шарде-«Москва» окажется большая доля онлайн-курьеров и QPS. Лечение:
- режем крупные города на подзоны (округа / полигоны доставки), не держим «всю Москву» одним ключом;
- мелкие города можно класть в общий шард «регион», чтобы не плодить пустые ноды;
- ребалансировка идёт по зоне: добавили подзону — переехал только её набор курьеров, а не 1/N всех id.

В Kafka из гео уходит **не живая точка** (она пишется сразу в Redis зоны), а поток для истории и аналитики.

## 4. Кэширование

Кэш — это несколько уровней, не один Redis на всё.

| Уровень | Что | Стратегия | TTL | Инвалидация |
|---------|-----|-----------|-----|-------------|
| **CDN / edge** | фото блюд и ресторанов (`photo_url`) | cache-on-edge | 1–24 ч | смена URL файла (content-hash в имени) или purge по событию меню |
| **Redis, каталог** | карточки ресторанов и меню | Cache-Aside | 5–15 мин | событие `MenuUpdated` |
| **Redis, правила цены** | `pricing_rules` | Cache-Aside | 1–3 мин | изменение правила |
| **Redis GEO** | текущие координаты | прямая запись | 30–60 сек | overwrite следующей точкой |
| **Redis, статус заказа** | ответ `GET /orders/{id}` | Cache-Aside | 10–30 сек | событие смены статуса |

**Сознательно не кэшируем:**
- платежи и hold/capture;
- `promo_codes.used_count` (только БД);
- accept/reject ресторана.

Промокод в Redis не крутим: инвариант «не больше N использований» должен переживать гонки двух заказов. Это `UPDATE promo_codes SET used_count = used_count + 1 WHERE used_count < max_uses` в PostgreSQL.

## 5. Очереди

Два разных профиля нагрузки — два брокера, не «Kafka на всё, потому что так в ДЗ 2».

| Поток | Брокер | Почему |
|-------|--------|--------|
| Доменные события саги, CQRS-проекции | **Kafka** | Высокий throughput, порядок внутри партиции (`key = orderId`), retention и replay, несколько независимых consumer group |
| Пуши, email, отложенный retry, DLQ уведомлений | **RabbitMQ** | Per-message TTL, delayed retry, routing keys, проще операционно на маленьком контуре. Kafka это умеет через костыли, но это не её сильная сторона |

**Почему не один брокер.**  
Kafka выигрывает на шине событий и повторном проигрывании истории. Минусы: тяжёлая эксплуатация, ребалансировка consumer group, нет нормального per-message delay/TTL.  
RabbitMQ выигрывает на «задачах с ретраями» (уведомления). Минусы: хуже replay большого лога, слабее как event store.  
NATS не берём как основной: мало retention и слабее модель для саги.

**Что именно едет в Kafka:** `OrderCreated`, `RestaurantAccepted`, `PaymentAuthorized`, `CourierAssigned`, `MenuUpdated`, а также **гео-история / аналитика**.  
**Что не едет в Kafka:** живой uplink координаты. Курьер пишет точку в Redis зоны напрямую (иначе трекинг опоздает на секунды консьюмера).

В публикаторах саги остаётся Transactional Outbox.

## 6. CAP trade-offs

CAP описывает только поведение при **разделении сети**. В обычном режиме важнее задержка — это уже **PACELC**:  
если partition — выбираем C или A; иначе (**E**lse) выбираем **L**atency или **C**onsistency.  
У нас в норме каталог и гео жертвуют строгостью ради короткого ответа (EL), заказ и оплата — ради корректности (EC).

### 6.1. Orders + Payments — при разделении предпочитаем C

Это не «PostgreSQL = автоматически CP». Обычный primary + async replica:
- чтение с реплики даёт stale read;
- если primary умер до отправки WAL — теряем и кусок C, и запись (A тоже нет).

Как делаем ближе к CP на этом контуре:
- критичные чтения (статус платежа, «списали или нет») — **с primary** или read-your-writes через тот же узел, что писал;
- у Payments — **синхронная реплика в другой AZ**: коммит только после записи на replica;
- при невозможности набрать кворум записи **отказываем** в операции, а не пишем «в одну ноду наугад».

### 6.2. Каталог — AP при разделении

Витрина должна открываться. Отдаём Redis / read-реплику, меню может быть на минуты старше. Цену при создании заказа всё равно перепроверяем.

### 6.3. CourierGeo — AP

Точка на карте может отстать на несколько секунд. Главное — отвечать. При разделении зоны клиент видит последнюю известную координату или заглушку «курьер в пути».

### 6.4. Chats — не «AP потому что Mongo»

Запись в primary Mongo при потере majority недоступна (это ближе к CP на запись).  
«Порядок сообщений» — это ordering, не C из CAP.

Сценарий при разделении:
- **читать** историю можно со secondary (история может быть неполной) — доступность чтения;
- **писать** новое сообщение нельзя, пока нет primary/majority — не плодим расходящиеся ветки чата.

### 6.5. Pricing при создании заказа (связка §4 и §6)

Если PricingService недоступен в момент `POST /orders`:

1. Пробуем кэш правил в Redis.
2. Если кэша нет — **не создаём заказ** с «примерно такой» ценой (это путь к спору и неправильному hold).
3. Если кэш есть — считаем по нему, кладём результат в `pricing_snapshot`, заказ создаём. Расхождение с истиной ловим короткой проверкой, когда Pricing вернётся; при расхождении выше порога — 409 / компенсация, не молчальное списание.
4. Счётчик промокода без PostgreSQL **не списываем**. Нет PG — промо не применяем либо заказ отклоняем.

Итого: каталог и гео при partition деградируют и остаются доступны. Заказ без цены и оплата без кворума — нет.
