## Исходные данные и допущения

| Параметр | Значение |
|----------|----------|
| MAU | 5 000 000 |
| DAU | 500 000 |
| Частота заказов | 2 заказа на пользователя в неделю |
| Peak factor | ×3 (обед и вечер) |
| Дней в месяце | 30 |
| Секунд в сутках | 86 400 |

**Как считаем число заказов.**  
«2 заказа на пользователя в неделю» применяем к DAU, а не к MAU. Иначе получилось бы ~1,4 млн заказов в день при DAU всего 500 тыс. — это значит, что каждый зашедший в приложение человек делает почти 3 заказа за день. Так не бывает.

```
заказов_в_день = DAU × 2 / 7
               = 500 000 × 2 / 7
               = 142 857 ≈ 143 000
```

```
заказов_в_месяц = 143 000 × 30 = 4 290 000
заказов_в_год   = 143 000 × 365 ≈ 52,2 млн
```

```
avg_rps = события_в_день / 86 400
peak_rps = avg_rps × 3
```

Допущения по размерам (чтобы расчёты можно было проверить):

| Объект | Размер |
|--------|--------|
| Запись заказа (заказ + позиции + адрес + снимок цены) | 8 КБ |
| Платёжная запись | 1 КБ |
| Позиция меню (текст) | 2 КБ |
| Фото блюда (сжатое) | 200 КБ |
| Карточка ресторана | 5 КБ |
| Гео-точка курьера | 100 байт |
| Сообщение чата | 1 КБ |
| JSON-ответ каталога (список ресторанов) | 50 КБ |
| JSON-ответ меню одного ресторана | 30 КБ |
| JSON-ответ статуса заказа | 3 КБ |

Оценка каталога: 20 000 ресторанов, в среднем 80 позиций, у 70% позиций есть фото.

## 1. Расчёт RPS

### 1.1. Сколько запросов делает один DAU за день

| Действие | Запросов / DAU / день | Тип |
|----------|----------------------|-----|
| Список ресторанов / фильтры / поиск | 8 | read |
| Открытие карточки ресторана + меню | 6 | read |
| Фото блюд (через CDN, но считаем запросы origin+CDN) | 15 | read |
| Расчёт цены в корзине | 3 | read (gRPC внутри) |
| Создание заказа | 143 000 / 500 000 ≈ 0,29 | write |
| Статус / история заказа | 8 | read |
| Трекинг курьера (HTTP-poll fallback; основной канал — WS) | 10 | read |
| Чат (только часть заказов) | 2 | read/write |
| Прочее (профиль, промо) | 3 | read |

Итого примерно **55 запросов на DAU в день**, из них ~0,3 записи заказа.

### 1.2. Таблица RPS по ключевым эндпоинтам

| Эндпоинт | Событий / день | Avg RPS | Peak RPS (×3) | Тип |
|----------|----------------|---------|---------------|-----|
| `GET /restaurants` (выдача каталога) | 500 000 × 8 = 4 000 000 | 46 | **139** | read |
| `GET /restaurants/{id}/menu` | 500 000 × 6 = 3 000 000 | 35 | **104** | read |
| `GET` фото блюд | 500 000 × 15 = 7 500 000 | 87 | **260** | read |
| `POST /orders` | 143 000 | 1,7 | **5** | write |
| `GET /orders/{id}` (статус) | 143 000 × 8 = 1 144 000 | 13 | **40** | read |
| `GET /orders` (история) | 500 000 × 1 = 500 000 | 6 | **17** | read |
| Pricing gRPC (внутри) | 500 000 × 3 + 143 000 ≈ 1 643 000 | 19 | **57** | read |
| `POST /partners/orders/{id}/accept` | ≈ 143 000 | 1,7 | **5** | write |
| Payments authorize/capture | ≈ 143 000 × 2 = 286 000 | 3,3 | **10** | write |
| CourierGeo uplink (MQTT/HTTP batch) | см. ниже | — | **2 000** | write |
| CourierGeo downlink / tracking | активные доставки × клиенты | — | **1 500** | read (WS) |
| Chat messages | 143 000 × 0,3 × 6 ≈ 257 000 | 3 | **9** | write |

**Гео-апдейты отдельно**, потому что это не классический HTTP RPS, но нагрузка большая:

```
онлайн-курьеров в пик ≈ 15 000
апдейт каждые 5 секунд
peak_geo_write = 15 000 / 5 = 3 000 сообщений/сек
```

Берём с запасом **2 000–3 000 RPS** на uplink. Downlink идёт не всем DAU, а только тем, у кого заказ в доставке:

```
одновременно в доставке ≈ заказов_в_пик_час / длительность_доставки
пик заказов в час = 143 000 / 24 × 3 ≈ 17 900
средняя доставка 40 мин → одновременно ~12 000 трекингов
```

### 1.3. Сводка

| Контур | Peak RPS |
|--------|----------|
| Каталог (read, без картинок) | ~240 |
| Картинки меню | ~260 |
| Заказы + статусы | ~60 |
| Платежи | ~10 |
| Гео | 2 000–3 000 |
| Чат | ~10 |
| **HTTP API суммарно (без гео и картинок)** | **~350** |
| **С картинками и гео** | **~2 500–3 500** |

Пишет мало, читает много. Узкое место по RPS — каталог и гео, не создание заказа.

## 2. Расчёт хранилища

### 2.1. Горячие операционные данные

**Заказы (Orders + items + history)**

```
52,2 млн заказов/год × 8 КБ = 417 600 000 КБ ≈ 400 ГБ / год
с индексами, TOAST и запасом × 2 ≈ 800 ГБ / год
за 3 года ≈ 2,4 ТБ
```

**Платежи**

```
52,2 млн × 1 КБ × 2 (реплика/аудит) ≈ 100 ГБ / год
за 3 года ≈ 300 ГБ
```

**Каталог (текст)**

```
20 000 ресторанов × 5 КБ = 100 МБ
20 000 × 80 позиций × 2 КБ = 3,2 ГБ
с версиями меню и индексами ≈ 15 ГБ (растёт слабо)
```

**Курьеры + назначения**

```
50 000 курьеров × 2 КБ + 52 млн назначений × 0,5 КБ ≈ 26 ГБ / год
```

**Чаты** (пишем не по каждому заказу, а по ~30%)

```
52,2 млн × 0,3 × 8 сообщений × 1 КБ ≈ 125 ГБ / год
за 3 года ≈ 375 ГБ
```

### 2.2. Медиа (фото меню) — основной объём

```
20 000 ресторанов × 80 позиций × 0,7 × 200 КБ
= 1 120 000 × 200 КБ
= 224 000 000 КБ ≈ 224 ГБ сырых файлов
```

С репликацией объектного хранилища (×2) и несколькими размерами (thumb 40 КБ + full 200 КБ):

```
224 ГБ × 1,2 (thumbs) × 2 (реплика) ≈ 540 ГБ
```

Каталог обновляется, но не растёт как заказы. За 3 года с ростом числа ресторанов ×1,5 → **~800 ГБ**.

### 2.3. Гео-история

Текущие координаты живут в Redis и почти не занимают диск (15 000 × 100 байт ≈ 1,5 МБ).

Если пишем историю (1 точка / 10 сек, 8 часов смены, 15 000 курьеров):

```
15 000 × (8 × 3600 / 10) × 100 байт ≈ 4,3 ГБ / день
≈ 1,6 ТБ / год
```

Имеет смысл хранить сырую историю 14–30 дней, дальше агрегировать или удалять. Для оценки на 1 год без усечения — 1,6 ТБ; с retention 30 дней — **~130 ГБ**.

### 2.4. Итого хранилище

| Тип | 1 год | 3 года | Где |
|-----|-------|--------|-----|
| Заказы (PG, с запасом) | 0,8 ТБ | 2,4 ТБ | PostgreSQL |
| Платежи | 0,1 ТБ | 0,3 ТБ | PostgreSQL |
| Каталог + партнёры | 0,02 ТБ | 0,03 ТБ | PostgreSQL |
| Чаты | 0,13 ТБ | 0,4 ТБ | MongoDB |
| Фото меню | 0,5 ТБ | 0,8 ТБ | Object Storage |
| Гео-история (с TTL 30 дней) | 0,13 ТБ | 0,13 ТБ | Timescale / cold |
| Бэкапы (×1 от горячих БД) | ~1,1 ТБ | ~3,1 ТБ | Object Storage |
| **Всего полезного** | **~1,7 ТБ** | **~4,1 ТБ** | |
| **С бэкапами и репликами БД (×2–3)** | **~4 ТБ** | **~10 ТБ** | |

Это не Instagram: у нас нет петабайт пользовательских фото. Основной рост — таблица заказов и бэкапы.

## 3. Bandwidth

### 3.1. Egress (главная статья)

**Каталог JSON**

```
(4 000 000 × 50 КБ + 3 000 000 × 30 КБ) / день
= 200 ГБ + 90 ГБ = 290 ГБ / день
```

**Фото блюд** (если все идут с origin)

```
7 500 000 × 200 КБ = 1 500 000 000 КБ ≈ 1 430 ГБ / день ≈ 1,4 ТБ / день
```

**Статусы и прочий API**

```
1 144 000 × 3 КБ + 500 000 × 8 КБ ≈ 7 ГБ / день
```

**Трекинг (WS, координаты)**

```
12 000 клиентов × 12 часов × 3600 / 5 сек × 0,2 КБ ≈ 21 ГБ / день
```

**Итого egress без CDN:**

```
~1,7 ТБ / день × 30 = 51 ТБ / месяц
```

Почти всё — картинки меню. JSON и статусы на этом фоне мелочь.

Ingress (загрузка фото партнёрами, гео uplink) на порядки меньше, в облаках обычно бесплатный или дешёвый.

### 3.2. Пиковая полоса

```
peak_фото_RPS 260 × 200 КБ ≈ 52 МБ/с ≈ 420 Мбит/с
peak_JSON_RPS 240 × 40 КБ ≈ 10 МБ/с ≈ 80 Мбит/с
peak_гео 3 000 × 200 байт ≈ 0,6 МБ/с
```

Нужен канал **~0,5–1 Гбит/с** на пике, если картинки отдаём сами. С CDN пик на origin падает в 10+ раз.

Цены — ориентиры лекции 22, чтобы цифры проверялись по той же методике. Для Yandex Cloud порядок тот же, в рублях выходит сопоставимо.

| Ресурс | Ставка |
|--------|--------|
| vCPU-час (on-demand) | $0,04 |
| RAM условно входит / или +$0,005 за GB-час | — |
| Managed DB | ~2× от compute той же мощности |
| Object Storage hot | $0,023 / GB-мес |
| Object Storage cold | $0,004 / GB-мес |
| Egress origin | $0,08 / GB |
| CDN egress | $0,03 / GB |
| Часов в месяце | 730 |

### 5.1. Compute

```
90 vCPU × $0,04 × 730 ≈ $2 628
```

С managed Kubernetes / балансировщиками округляем до **$3 200**.

### 5.2. Managed DB + Redis + Kafka + Mongo

```
PG + Redis + Kafka + Mongo ≈ $4 500 … $6 000
```

Берём **$5 500** (как «managed services ~$6k» в примере лекции, у нас данных меньше, чем у «Кадра»).

### 5.3. Storage

```
Hot object + SSD (фото, бэкапы, 2 ТБ) : 2 000 GB × $0,023 = $46
Cold / архив 2 ТБ                      : 2 000 GB × $0,004 = $8
```

Хранилище само по себе дешёвое. **~$100–200** вместе с снапшотами.

### 5.4. Сеть (без CDN)

```
51 000 GB × $0,08 = $4 080
```

Картинки с origin — главная сетевая статья, но не 92% счёта, как в Instagram-like системе. У нас нет петабайт фото пользователей.

### 5.5. Сводка «как есть» (без оптимизаций)

| Статья | $/мес | Доля |
|--------|-------|------|

**Yandex Cloud (порядок):**

## 6. Оптимизация (без потери качества)

### 6.1. CDN для фото меню — главный рычаг

90%+ картинок уходит в CDN (как в лекции: 90–95% offload).

```
остаток на origin: 10% × 1,4 ТБ/день × 30 = 4,2 ТБ
CDN: 46,8 ТБ × $0,03 = $1 404
origin: 4 200 GB × $0,08 = $336
итого сеть ≈ $1 740 вместо $4 080
экономия ≈ $2 300 / мес (~17% счёта)
```

Качество не падает — клиенту картинки даже приезжают быстрее.

### 6.2. Кэш каталога (уже заложен в ДЗ 2–3)

Cache-Aside в Redis, TTL 5–15 мин, инвалидация по `MenuUpdated`.

Если попадание в кэш 80–90%, RPS в PostgreSQL каталога падает с ~240 до ~25–50. Можно держать меньше реплик PG и меньше подов Handbooks.

```
экономия compute+DB каталога ≈ $400–700 / мес
```

### 6.3. Reserved / committed use на базу (стабильная нагрузка)

Базы и Kafka работают 24/7. Reserved на 1 год: −30…−40%.

```
$5 500 × 0,35 ≈ $1 900 / мес
```

Пиковые API-поды оставляем on-demand + autoscaling.

### 6.4. Spot / preemptible для воркеров

Outbox-релеер, рассылка пушей, пересчёт прайса, ETL гео-истории — stateless, можно ронять.

```
3–5 воркеров × ~$80 ≈ $250–400 / мес
```

Минус 70% на этой пачке → экономия **~$250 / мес**.

### 6.5. Tiering и TTL

- Гео-история: хранить 14–30 дней, не год. Экономим ~1,5 ТБ/год диска и IOPS.
- Бэкапы старше 30 дней — в cold storage.
- Старые заказы (> 18 месяцев) — в архивную БД / object storage, в оперативном PG только «горячий» горизонт.

```
экономия storage небольшая в деньгах (~$50–100), но сильно дешевле будущий вертикальный рост PG
```

### 6.6. Не делать лишнюю «девятку»

99,9% (Multi-AZ, N+1) достаточно. 99,99% / multi-region для доставки еды почти никогда не окупается: час простоя дорог бизнесу, но не настолько, чтобы платить за вторую географию.

Это скорее «не увеличивать счёт», чем прямая экономия.

### Итог после оптимизаций

| Шаг | Экономия $/мес |
|-----|----------------|
| CDN на фото | 2 300 |
| Reserved на DB/Kafka | 1 900 |
| Кэш каталога (меньше PG/подов) | 500 |
| Spot для воркеров | 250 |
| Cold storage / TTL | 80 |
| **Сумма** | **~5 000** |

```
было   ≈ $13 800
стало  ≈ $8 800
Cost/DAU ≈ $0,018
```

Качество для клиента не режем: картинки быстрее, каталог по-прежнему из кэша, заказ и оплата остаются на CP-контуре с Multi-AZ.
