## 1. Отказоустойчивость

### 1.1. RTO и RPO по сервисам

RTO — сколько система может быть недоступна.  
RPO — сколько данных допустимо потерять.

| Сервис | Tier | RTO | RPO | Обоснование |
|--------|------|-----|-----|-------------|
| PaymentsService | 0 | 5 мин | ≈ 0 | Деньги. Потеря подтверждённого платежа = двойное списание и разбор с банком. Синхронная реплика. |
| OrdersService | 0 | 10 мин | секунды | Без приёма заказов сервис стоит. Лаг статуса на секунды терпим, потеря уже созданного заказа — нет. |
| PartnersService (accept/reject) | 1 | 15 мин | минуты | Ресторан не подтверждает заказ — шаг саги встаёт. Компенсация по таймауту уже есть. |
| RestaurantsHandbooksService | 1 | 5 мин | 15 мин | Витрина должна открываться. Устаревшее меню из Redis допустимо: цену перепроверяем при заказе. |
| PricingService | 1 | 10 мин | 15 мин | Правила меняются редко. Кэш правил можно использовать. Счётчик промокода без PG не списываем. |
| CouriersService | 1 | 15 мин | минуты | Нет назначения — заказ не едет. Сага компенсирует. |
| CourierGeoService | 2 | 15 мин | 1–2 мин | Точка на карте может пропасть. Заказ при этом жив. |
| ChatsService | 2 | 30 мин | минуты | Деградация: «напишите в поддержку». |
| NotificationsService | 2 | 30 мин | минуты | Пуш можно дослать позже, заказ не блокируем. |

Целевой SLA контура заказ+оплата: **99,9%** (~8,8 часа простоя в год). 99,99% не берём.

### 1.2. Репликация критичных БД

Реплика спасает от падения узла и зоны. От `DELETE` и кривой миграции — нет, для этого бэкап + PITR.

| Кластер | Репликация | Control / routing | Практический RPO |
|---------|------------|-------------------|------------------|
| PostgreSQL Payments | primary + **sync** replica в другой AZ + 1 async | Patroni + PgBouncer | ≈ 0, пока жив sync |
| PostgreSQL Orders | primary + semi-sync в другой AZ + async | Patroni + PgBouncer | секунды |
| PostgreSQL Catalog / Partners / Couriers | async replica в другой AZ | Patroni | минуты |
| Redis (кэш + GEO) | Cluster / Sentinel, 3 ноды, 2 AZ | сам кластер | минуты; кэш прогревается |
| MongoDB Chats | replica set, 3 ноды, majority write | драйвер | секунды на запись |
| Kafka | RF = 3, `min.insync.replicas = 2` | сам кластер | ≈ 0 для подтверждённых сообщений |
| RabbitMQ (уведомления) | quorum queue, 3 ноды | сам кластер | секунды |

Правило 3-2-1 для Orders и Payments: 3 копии, 2 носителя, 1 копия off-site (другая зона / бакет).  
Бэкап: полный раз в сутки + непрерывный WAL. Раз в месяц — restore-тест, иначе RTO/RPO бумажные.

Критичные чтения (статус платежа, «списали или нет») идут с **primary**, не с async-реплики.

### 1.3. Паттерны отказоустойчивости

| Паттерн | Где | Как |
|---------|-----|-----|
| Timeout | все исходящие вызовы | Payments → банк: 3 с. Orders → Pricing: 200 мс. APNs: 2 с. |
| Retry + backoff | только идемпотентные | 3 попытки, exp backoff + jitter, `Idempotency-Key`. 4xx не ретраим. |
| Circuit breaker | Payments → провайдер, Notifications → APNs, Orders → Pricing | после N ошибок — fail-fast. Pricing: кэш правил. Банк: заказ остаётся `PENDING`. |
| Bulkhead | пулы соединений и очереди | отдельные пулы каталог / заказы / платежи / гео. Падение гео не забирает коннекты Orders. |
| Idempotent consumer | все читатели Kafka | ключ `eventId`. |
| Деградация | каталог, гео, чат, Pricing | каталог из Redis; гео — «курьер в пути» без точки; чат — баннер поддержки; Pricing — кэш правил, без кэша заказ не создаём. |

### 1.4. План DR (падение региона)

Схема — **Pilot Light / Warm Standby**, не active-active.

```
Регион A (основной)                         Регион B (DR)
AZ-1                AZ-2                    минимальное ядро
PG Payments ──sync──► replica               async replica Payments
PG Orders   ──semi──► replica               async replica Orders
Kafka RF=3, Redis, API                      WAL + бэкапы в Object Storage
                                            k8s ×1 / выключен
                 DNS / Gateway failover ──────────────────►
```

Падение региона = обе AZ основной площадки недоступны > 10 минут. Падение одной AZ закрывает Patroni внутри региона (RTO минуты), это не DR.

**Runbook:**
1. Дежурный отличает «умерла AZ» от «умер регион».
2. Статус-страница: приём новых заказов ограничен.
3. Promote async-реплик Payments и Orders в регионе B. Фактический RPO = лаг реплики.
4. Переключаем DNS / Gateway.
5. Redis и Kafka — из снапшота + догон outbox.
6. Каталог — из бэкапа и Redis, витрина может быть старой.
7. Гео и чат в первые 15–30 мин можно не поднимать.
8. Сверка платежей с реестром провайдера (хвост WAL).
9. Обратный переезд — только планово, в низкий час.

Раз в квартал — game day с замером реального RTO.

## 2. Observability

### 2.1. Метрики (RED + USE + бизнес)

Латентность — перцентили, не среднее. 4xx / 5xx / таймауты раздельно.

| Сервис / ресурс | Метод | Метрика | Как меряем | Зачем |
|-----------------|-------|---------|------------|-------|
| API Gateway | RED | request rate по маршруту | `http_requests_total` / сек | виден пик обеда, есть ли трафик вообще |
| API Gateway | RED | доля 5xx и отдельно 4xx | errors / all, 3–5 мин | 5xx — наша вина; 4xx — клиент/валидация |
| API Gateway | RED | p95 / p99 latency | гистограмма | симптом «приложение тормозит» |
| OrdersService `POST /orders` | RED | p99 latency | гистограмма по эндпоинту | узкое место оформления |
| OrdersService | RED | таймауты к Pricing / PG | counter | отделяем зависимость от своего бага |
| PaymentsService | RED | rate authorize/capture + доля fail | counters | деньги: провайдер или мы |
| RestaurantsHandbooksService | RED | p95 выдачи меню | гистограмма | витрина для всех DAU |
| CourierGeoService | RED | rate uplink + p99 доставки точки клиенту | counter + histogram | трекинг жив |
| ChatsService | RED | error rate send message | counter | чат деградировал |
| PostgreSQL Payments | USE | utilization пула соединений | % занятых | до отказа «too many connections» |
| PostgreSQL Orders | USE | replication lag, сек | `pg_stat_replication` | растёт фактический RPO |
| PostgreSQL | USE | disk utilization + IOPS | node exporter | место кончится раньше, чем RPS |
| Redis | USE | evicted_keys, hit ratio | INFO | каталог бьёт в PG мимо кэша |
| Kafka `order-events` | USE | consumer lag | burrow / exporter | сага и пуши отстают |
| RabbitMQ notifications | USE | глубина очереди + DLQ | queue depth | ретраи не разгребаются |
| CPU / RAM подов | USE | utilization % | cAdvisor | saturating до OOM |
| Thread / event-loop queue | USE | длина очереди | runtime metrics | saturation до роста p99 |
| Бизнес | golden | успешные заказы / мин | counter | ценность для пользователя |
| Бизнес | golden | успешные оплаты / мин | counter | деньги |
| Бизнес | golden | доля компенсаций саги | compensations / created | поток ломается системно |

### 2.2. Алерты

Пороги от SLO и профиля нагрузки (пик каталога — сотни RPS, `POST /orders` ~5 RPS). Окно 3–5 мин — чтобы не будить на одиночный всплеск.

**Название:** p99 `POST /orders` выше SLO  
**Условие/порог:** p99 > 400 мс в течение 5 мин  
**Severity:** critical  
**Что означает:** оформление заказа для клиента медленное или «крутится».  
**Вероятная причина:** Pricing, пул PG Orders, шаг саги.  
**Реакция:** графики Pricing и PG → если Pricing — открыть circuit и деградация на кэш правил → если деплой — откат.  
**Кому:** on-call backend

**Название:** рост 5xx на API Gateway  
**Условие/порог:** доля 5xx > 2% трафика 3 мин  
**Severity:** critical  
**Что означает:** часть пользователей получает отказ.  
**Вероятная причина:** упавшая зависимость, переполненный пул, плохой деплой.  
**Реакция:** последний релиз → статус Payments/Orders/PG → откат деплоя.  
**Кому:** on-call backend

**Название:** доля неуспешных оплат  
**Условие/порог:** `payments_failed / payments_attempted` > 5% за 5 мин  
**Severity:** critical  
**Что означает:** люди не могут заплатить.  
**Вероятная причина:** провайдер, circuit уже должен открыться, нехватка идемпотентности.  
**Реакция:** стоп новых списаний (circuit), заказы не двигаем из `PENDING`, сверка с кабинетом провайдера.  
**Кому:** on-call payments + backend

**Название:** отставание саги (lag Kafka)  
**Условие/порог:** lag `order-events` > 10 000 сообщений 10 мин  
**Severity:** warning (в обед — critical)  
**Что означает:** статусы, пуши и назначение курьера приезжают с задержкой.  
**Вероятная причина:** медленный consumer, poison message, ребалансировка.  
**Реакция:** доскейлить consumer → DLQ → не рестартить брокера «на всякий».  
**Кому:** on-call backend

**Название:** лаг реплики Payments  
**Условие/порог:** `replication_lag_seconds` > 30 сек 3 мин  
**Severity:** critical  
**Что означает:** фактический RPO уехал; failover на эту реплику потеряет платежи.  
**Вероятная причина:** сеть между AZ, тяжёлый запрос, replica отстала.  
**Реакция:** не делать planned failover; убрать аналитику с реплики; проверить диск.  
**Кому:** on-call DBA / backend

**Название:** промах кэша каталога  
**Условие/порог:** Redis hit ratio < 60% 10 мин  
**Severity:** warning  
**Что означает:** витрина начинает тормозить, нагрузка уезжает в PG.  
**Вероятная причина:** шторм инвалидации `MenuUpdated`, вытеснение ключей.  
**Реакция:** проверить частоту MenuUpdated → прогрев ключей.  
**Кому:** backend (ночью не будить, если p99 витрины в норме)

**Название:** гео-поток остановился при живых доставках  
**Условие/порог:** `geo_updates_total` ≈ 0 при > 1000 активных доставках, 3 мин  
**Severity:** warning  
**Что означает:** карта у клиента замерла. Заказ при этом может быть жив.  
**Вероятная причина:** MQTT/Geo-поды, не Orders.  
**Реакция:** деградация «без точки»; не рестартить весь контур заказа.  
**Кому:** on-call backend

| Алерт | Порог | Severity | Симптом | Реакция |
|-------|-------|----------|---------|---------|
| p99 POST /orders | > 400 мс, 5 мин | critical | заказ не создаётся вовремя | Pricing / PG / откат |
| 5xx Gateway | > 2%, 3 мин | critical | отказы пользователям | деплой / зависимости |
| fail оплат | > 5%, 5 мин | critical | нельзя заплатить | circuit, PENDING |
| lag order-events | > 10k, 10 мин | warning/critical | статусы опаздывают | consumer / DLQ |
| lag реплики Payments | > 30 с, 3 мин | critical | риск потерять платежи | не failover |
| hit ratio каталога | < 60%, 10 мин | warning | витрина тупит | инвалидация / прогрев |
| geo rate = 0 | 3 мин при активных доставках | warning | нет точки на карте | только гео-контур |

### 2.3. Логи и трейсы

**Логи:** `request_id`, `user_id` из JWT, `order_id`, код, latency; шаги саги и компенсации; вызовы провайдера без карточных данных; `eventId` консьюмера; audit accept/reject и отмен.

Не пишем в логи: PAN/CVV (их нет), полные токены, сырой адрес в долгоживущих логах.

**Трейсы (OpenTelemetry):** `trace_id` от Gateway через Orders → Pricing → Payments; спаны публикации/чтения Kafka; атрибут `order_id`.  
Сэмпл: 1% успешных, 100% ошибок и все `POST /orders` / платежи.

## 3. Тестирование

### 3.1. Нагрузочное тестирование

Цифры сайзинга: ~143k заказов/сутки, пик ×3, каталог — основной read.

| Сценарий | Нагрузка | Успех |
|----------|----------|-------|
| Каталог, вечерний пик | ~140 RPS списков + ~100 RPS меню, hit ratio ≥ 80% | p95 < 200 мс, 5xx < 0,5% |
| Оформление заказа | 5 RPS `POST /orders` + Pricing + Payments + accept | p95 < 400 мс, нет дублей с тем же Idempotency-Key, сага до `PREPARING` или честной компенсации |
| Гео | 15k курьеров, точка / 5 с (~3k msg/s) + 12k WS | p95 доставки точки < 1 с, дроп < 1%, p99 заказов не растёт (bulkhead) |
| Смешанный пик | каталог + заказы + гео | CP-контур жив, сценарий «заказ» не ломается |
| Soak 2 часа | 70% пика | нет утечки памяти, lag Kafka не растёт |

Стенд с анонимизированным слепком. Перед релизом — сценарии «каталог» и «заказ» на canary.

### 3.2. Chaos-эксперименты

Три разных типа отказа (не три раза kill пода). Формат — по шаблону курса.

```
Эксперимент №1: Kill primary PostgreSQL Orders
Steady state:    успешные POST /orders ≥ 4 / сек на стенде в пиковый час,
                 доля 5xx на /orders < 1%, дублей заказов = 0
Гипотеза:        при убийстве primary трафик переедет на semi-sync replica
                 за счёт Patroni + PgBouncer; RTO < 2 мин, RPO ≈ 0
Blast radius:    staging, только кластер Orders, Payments не трогаем
Метод:           kill контейнера/VM primary
Наблюдаем:       p99 POST /orders, 5xx Gateway, replication lag,
                 успешные заказы/мин, алерт «p99 POST /orders»
Rollback:        5xx > 5% дольше 3 мин или появились дубли заказов —
                 вернуть старый primary, остановить тест
Ожидаемый вывод: либо failover укладывается в RTO 10 мин из §1,
                 либо клиент висит на мёртвом primary — чинить routing plane
```

```
Эксперимент №2: Отказ платёжного провайдера
Steady state:    успешные оплаты/мин в норме стенда,
                 заказы не висят в PENDING дольше таймаута саги
Гипотеза:        при blackhole/5xx провайдера сработает timeout 3 с
                 + 3 retry с Idempotency-Key, затем circuit breaker;
                 заказ не спишется дважды и уйдёт в компенсацию
Blast radius:    staging, только outbound к sandbox-провайдеру,
                 fault injection на 10% заказов стенда
Метод:           toxiproxy: drop + 500 на 10 минут
Наблюдаем:       payments_failed, p99 POST /orders, compensations/min,
                 состояние circuit, алерт «доля неуспешных оплат»
Rollback:        компенсации > 30% или 5xx API > 5% — снимаем fault
Ожидаемый вывод: либо клиент честно видит «оплата не прошла»,
                 либо заказы вечно PENDING — дыра в таймауте/саге
```

```
Эксперимент №3: Lag консьюмера order-events
Steady state:    lag ≈ 0; доля заказов, дошедших до PREPARING за 3 мин, ≥ 95%
Гипотеза:        при отставании партиции outbox + at-least-once
                 + идемпотентный consumer догонят события
                 без двойного назначения курьера
Blast radius:    staging, одна партиция order-events, не весь кластер Kafka
Метод:           остановить consumer group на 5 мин, затем поднять;
                 отдельно — убить одного брокера (RF=3, min.isr=2)
Наблюдаем:       kafka consumer lag, compensations, дубли CourierAssigned,
                 алерт «отставание саги»
Rollback:        lag не падает 10 мин после старта consumer
                 или появились дубли назначений — стоп, вернуть брокера
Ожидаемый вывод: либо сага идемпотентна,
                 либо outbox/консьюмер теряют или двоят события
```

Не начинаем с «выключить регион» — это отдельный game day DR раз в квартал.

## 4. Безопасность (кратко)

**Аутентификация / авторизация**
- Клиент и курьер: OIDC, JWT (короткий access) + refresh.
- `userId` только из токена.
- Партнёрский кабинет — отдельный клиент, роли `partner` / `moderator`.
- Владелец видит только свой заказ; ресторан — только свои accept/reject.
- Внутри кластера: mTLS + сервисный аккаунт. gRPC Pricing/Geo наружу не торчат.

**Что шифруем**
- В транзите: TLS до клиента, PG, Redis, Kafka, RabbitMQ.
- На диске: PG, Mongo, диски брокеров, бакеты бэкапов и фото.
- Секреты — в vault / секрет-менеджере.
- Адрес и телефон — в Orders, в логах маскируем.
- Карты не храним: только токен провайдера и `provider_payment_id`.
